# Архитектура MVP

## Назначение документа

Этот документ фиксирует техническую структуру приложения, границы модулей и правила надёжной обработки аукционов. Функциональные требования и правила предметной области находятся в `AGENTS.md`; порядок работ — в `ROADMAP.md`.

Связанные документы:

- `DATABASE.md` — модель данных, ограничения и индексы;
- `TELEGRAM_FLOWS.md` — пользовательские Telegram-сценарии и callback-контракты.

## Контекст системы

Приложение — модульный монолит на Laravel. У него две внешние точки входа:

- Telegram Bot API принимает webhook и показывает пользователю аукционы в личном чате;
- Filament предоставляет администраторам веб-интерфейс для управления лотами, аукционами и оплатами.

PostgreSQL является единственным источником истины для состояния аукционов. Redis используется для очередей, Horizon и ограниченного кэша, но не хранит критическое бизнес-состояние. Файлы preview хранятся через Laravel Filesystem на локальном диске в MVP.

```text
Telegram ──webhook──> HTTP adapter ─┐
                                    ├── Application services ──> Domain
Filament ───────────> Admin adapter ┘              │
                                                   ├── PostgreSQL
                                                   ├── Domain events -> Queue -> Telegram notifications
                                                   └── Scheduler / delayed jobs
```

## Принципы

1. Состояние аукциона меняется только прикладными сервисами внутри транзакции PostgreSQL.
2. Транспортные слои не содержат бизнес-правил: Telegram и Filament преобразуют ввод в команды и отображают результат.
3. Цена и валидность ставки всегда рассчитываются по данным, заблокированным в БД; callback Telegram не является источником истины.
4. Все денежные значения — `bigint` в центах USD. `float` и `decimal` не используются.
5. Побочные эффекты выполняются после коммита и должны быть идемпотентны.
6. Важные сущности не удаляются физически: отмены и административные действия сохраняют историю.

## Слои и модули

Код располагается в `app/Modules/<Module>` и не зависит от порядка загрузки Laravel-моделей.

| Слой | Ответственность | Не должен знать |
| --- | --- | --- |
| Domain | Инварианты, enum, сущности, доменные события | HTTP, Telegram, Eloquent, очереди |
| Application | Команды, транзакционные use case, интерфейсы портов | Формат Telegram и Filament UI |
| Infrastructure | Eloquent-репозитории, файловое хранилище, Telegram API, очередь | Правила конкретного UI |
| Interfaces | Webhook-контроллеры, обработчики Telegram, Filament-ресурсы | Детали хранения и конкуренции |

Основные модули:

- `Auction` — проведение торгов, финализация и статусы;
- `Bid` — запись, отмена и ранжирование ставок;
- `Artwork` — метаданные лота и preview;
- `Participant` — пользователь Telegram, анонимный ID и Terms;
- `Purchase` — ручная оплата и предложение следующему участнику;
- `Notification` — постановка и доставка сообщений;
- `Telegram` — транспортный адаптер;
- `Admin` — Filament и аудит действий;
- `Shared` — деньги, время, транзакции, идентификаторы и общие исключения.

Зависимости направлены внутрь: `Interfaces → Application → Domain`. `Infrastructure` реализует порты Application и подключается через service providers.

## Модель состояний

```text
draft -> scheduled -> active -> awaiting_payment -> paid -> completed
                  \-> cancelled
active -----------> no_sale
awaiting_payment -> no_sale
```

`scheduled` становится `active` по времени или административному действию. При финализации без валидных ставок устанавливается `no_sale`; с валидной ставкой — `awaiting_payment`. `cancelled` доступен администратору до завершения сделки. Переходы проверяются отдельной политикой состояния, а не UI.

Ставки имеют состояния `active`, `outbid`, `winning`, `cancelled`, `disqualified`. Только одна активная ставка может быть текущим лидером аукциона. Отмена ставки не удаляет запись и запускает пересчёт актуального лидера в той же транзакции.

## Ключевые данные

Полная спецификация колонок и индексов должна поддерживаться в `database.md`. Базовые связи:

- `users` содержит `telegram_id` (уникальный), публичный `bidder_code`, текущую принятую версию Terms и дату принятия;
- `artworks` содержит описание и путь к preview; оригинал работы не хранится;
- `auctions` содержит правила торгов, статус, `current_price_cents`, `current_leader_id`, дату окончания и `version`;
- `bids` неизменно хранит сумму, участника, статус и причину административной отмены;
- `purchase_offers` фиксирует кому, за какую сумму и до какого срока предложена покупка;
- `processed_telegram_updates` гарантирует идемпотентность входящих updates;
- `telegram_messages`, `notifications` и `audit_logs` сохраняют доставку и историю действий.

В `auctions` победитель аукциона и покупатель разделены: `auction_winner_id`, `buyer_id`, `winning_bid_id`, `accepted_bid_id`. Это позволяет предложить покупку следующему участнику за сумму его собственной ставки, не изменяя историю торгов.

## Размещение ставки

Команда `PlaceNextBid` получает только `auctionId`, `userId` и версию отображённого экрана. Сумма не передаётся клиентом.

```text
BEGIN
  lock auction row FOR UPDATE
  проверить active, ends_at > now и Terms пользователя
  проверить версию callback (если устарела — вернуть актуальный экран)
  вычислить current_price + bid_increment
  создать bid
  пометить прежнюю ставку outbid
  обновить current_price, current_leader_id и version
  при необходимости продлить ends_at
  сохранить доменные события в outbox
COMMIT
после коммита: обработать outbox и поставить уведомления в очередь
```

Блокировка строки аукциона сериализует конкурирующие ставки одного аукциона. Разные аукционы обрабатываются параллельно. Время сравнивается с временем базы данных/приложения в UTC. Анти-снайпинг продлевает `ends_at` до `now + configured_extension_seconds`, если до конца осталось не больше настроенного порога.

## Доменные события и фоновые задачи

Сервисы публикуют доменные события, а не вызывают уведомления напрямую:

- `BidPlaced`;
- `AuctionExtended`;
- `AuctionFinished`;
- `PaymentConfirmed`.

Для надёжности события сначала сохраняются в транзакционной outbox-таблице. После коммита dispatcher передаёт их в Laravel Queue. Listener-ы создают уведомления и Telegram-задачи. Каждая задача имеет идемпотентный ключ, retry/backoff и безопасна при повторном запуске.

Завершение аукциона запускается двумя путями: отложенной `FinalizeAuctionJob` на `ends_at` и Scheduler раз в минуту. Оба вызывают один идемпотентный use case `FinalizeAuction`; он повторно блокирует аукцион и проверяет, что он ещё `active` и действительно завершился.

## Telegram-адаптер

Webhook проверяет secret token и немедленно сохраняет `update_id` в `processed_telegram_updates` с уникальным индексом. Повторный update завершается успешно без повторного выполнения команды.

Поток обработки:

```text
WebhookController -> UpdateRouter -> Command/Callback handler
                  -> Application command -> MessageRenderer -> TelegramClient
```

`CallbackQuery` содержит короткий подписанный идентификатор действия и версию представления. Перед выполнением действие авторизуется по Telegram user ID, но цена, статус и лидер всегда читаются из БД. Все Telegram-вызовы из listener-ов выполняются очередью; webhook не ожидает сетевую доставку уведомлений.

Подробные сценарии экранов, callback-данные и сообщения ведутся в `telegram_flows.md`.

## Администрирование и безопасность

Filament использует отдельную guard/модель администратора и policy для каждой операции. Изменение правил аукциона разрешено только пока нет ставок. Подтверждение платежа, отмена ставки, отмена аукциона и предложение покупки следующему участнику создают неизменяемую запись в `audit_logs` с инициатором, типом объекта, данными до/после и причиной.

Webhook защищён secret token; входящие запросы валидируются и ограничиваются по частоте. В логах и пользовательских сообщениях не раскрываются Telegram ID, username и полная история чужих ставок. Секреты находятся только в переменных окружения.

## Ошибки и наблюдаемость

Ожидаемые бизнес-ошибки (`AuctionNotActive`, `AuctionEnded`, `TermsNotAccepted`, `StaleAuctionView`) возвращаются адаптеру как типизированные результаты, а не как необработанные HTTP 500. Неожиданные ошибки логируются с correlation ID и попадают в стандартный мониторинг Laravel.

Horizon отслеживает очереди уведомлений и финализации. Dashboard отображает операционные показатели, а администратор видит failed jobs и журнал аудита. Критичные метрики: количество активных аукционов, задержка задач финализации, неотправленные уведомления, ожидающие оплаты и ошибки webhook.

## Тестовая стратегия

- Unit-тесты покрывают переходы состояний, расчёт цены, анти-снайпинг и отбор следующего покупателя.
- Feature-тесты покрывают транзакционные use case, Terms, оплату и административные действия.
- Интеграционные тесты проверяют webhook-идемпотентность, outbox, очереди и scheduler.
- Конкурентный тест размещает две ставки одновременно и подтверждает единственного лидера, корректную цену и историю.

Критерий готовности любого изменения: миграция, соответствующий use case, тесты и обновление документации, если изменилась модель, поток или архитектурное решение.
