# Выпуски-выставки в Telegram

## Статус решения

Этот документ расширяет MVP аукционов. Filament остаётся интерфейсом куратора для создания работ, выпусков, расписания и аукционов. Ставка остаётся только фиксированным шагом: произвольный ввод суммы не поддерживается.

Выпуск — общий календарь событий для всех его подписчиков. Он не является персональной цепочкой сообщений и не воспроизводится заново для поздно присоединившегося зрителя.

## Поведение зрителя

- `/start` создаёт или обновляет пользователя и подписывает его на текущий выпуск одним действием.
- Зритель, присоединившийся после начала выпуска, получает только тихое короткое приветствие и будущие события. Пропущенные работы не досылаются.
- Работа приходит обычным сообщением без служебного заголовка, кнопок, цены и слова «лот». Доставка обычная, со звуком.
- Экспликация приходит в заданный куратором момент. Она тихая (`disable_notification`) и является reply к сообщению конкретной работы у конкретного зрителя. Зритель не может ускорить её получение.
- Сообщение работы с ограниченным сроком жизни удаляется ботом в заданный момент. Если экспликация должна прийти после удаления, она отправляется отдельным сообщением без reply.
- Перед открытием торгов отдельное громкое сообщение-каталог перечисляет все работы выпуска как лоты: автор, название, условия владения, стартовая цена и правило продления. Это единственная точка, в которой поздний зритель видит пропущенные работы.

## Модель данных

### `releases`

Выпуск: `title`, `status` (`draft`, `scheduled`, `running`, `completed`, `cancelled`), `starts_at`, `ends_at`, `timeline_scale_basis_points`, `created_by_admin_id`.

`timeline_scale_basis_points` — целое число без float: `10000` означает обычное время. Масштаб применяется при создании или импорте расписания, а не в момент исполнения уже созданного события.

### `release_artworks`

Связь работы с выпуском: `release_id`, `artwork_id`, `position`. Она определяет состав каталога; расписание доставки задаётся событиями ниже.

### `release_events`

Единое серверное расписание: `release_id`, опциональные `artwork_id` и `auction_id`, `type`, `scheduled_at`, `notification_mode`, `payload`, `status`, `attempts`, `processed_at`.

Допустимые типы MVP:

- `deliver_artwork`;
- `deliver_explanation`;
- `delete_artwork_message`;
- `send_catalog`;
- `activate_auction`.

Событие имеет уникальный `(release_id, sequence)` и исполняется идемпотентно. `payload` хранит редакционный текст и параметры конкретного события, не авторитетные цену или статус аукциона.

### `release_subscriptions`

Подписка пользователя на выпуск: `release_id`, `user_id`, `subscribed_at`, `unsubscribed_at`. Получателями события становятся только подписки с `subscribed_at <= release_events.scheduled_at` и без отписки на момент события. Это исключает досылку истории позднему зрителю.

### `release_deliveries`

Идемпотентность fan-out по получателям: `release_event_id`, `user_id`, `telegram_message_id`, `status`, `sent_at`, `failed_at`, `failure_reason`.

Для `deliver_artwork` эта таблица хранит message ID конкретной работы у конкретного пользователя. Он необходим для reply экспликации и `deleteMessage`.

## Сервисы, задания и очередь

1. `SubscribeToCurrentRelease` — создаёт подписку без ретроспективной доставки.
2. `ClaimDueReleaseEvents` — выбирает просроченные события с блокировкой и ставит обработку в очередь.
3. `DeliverReleaseEvent` — создаёт `release_deliveries` с уникальным ключом и рассылает событие только допустимым подписчикам.
4. `DeliverArtwork`, `DeliverExplanation`, `DeleteArtworkMessage`, `SendReleaseCatalog`, `ActivateReleaseAuction` — отдельные use case; transport Telegram остаётся адаптером.
5. Scheduler запускает поиск due-событий каждую минуту в production и каждую секунду в demo-режиме. Для точности также ставится delayed job на `scheduled_at`; оба пути вызывают один идемпотентный сервис.
6. Fan-out всегда выполняется очередью. Задания имеют retries/backoff и ограничитель Telegram API; состояние доставки записывается независимо от аукционной транзакции.

## Telegram-контракт

`TelegramBotApiClient` расширяется методами `sendPhoto`, `deleteMessage` и `sendChatAction`. Он принимает `reply_to_message_id` и `disable_notification`, а после отправки возвращает `message_id`.

`sendMessageDraft` не входит в первый инкремент: его доступность и совместимость с текущей версией Bot API должны быть отдельно подтверждены перед использованием.

## Интеграция с аукционом

- Каталог читает цену, валюту, фиксированный шаг и anti-sniping только из БД аукционов.
- Открытие торгов выполняется существующим переходом `scheduled -> active`; событие выпуска лишь вызывает use case.
- Callback «+ шаг» передаёт только идентификатор аукциона и версию экрана. Ожидаемая цена всегда пересчитывается внутри транзакции с блокировкой аукциона.
- Уведомление о перебитой ставке остаётся громким и адресуется только затронутому участнику.

## Сквозной demo-сценарий

Телефон A подписывается -> работа 1 -> тихая экспликация-reply -> работа 2 -> удаление работы 2 -> телефон B подписывается и не получает историю -> работа 3 приходит A и B -> каталог -> открытие аукциона -> две ставки -> перебитие -> продление -> закрытие -> уведомление победителю -> отложенное сообщение через 10 минут.

## Наблюдаемость и тесты

Журнал должен позволять увидеть время подписки, событие расписания, recipient delivery, Telegram message ID, удаление и ставку.

Pest feature-тесты обязаны покрыть:

- отсутствие ретроспективной доставки позднему подписчику;
- одинаковый набор получателей события в общем календаре;
- reply экспликации на персональное сообщение работы;
- отправку экспликации без reply после удаления работы;
- идемпотентный повтор scheduler/job;
- ограничение скорости fan-out;
- каталог и переход аукциона в `active`;
- сохранение существующей конкуренции ставок и anti-sniping.
